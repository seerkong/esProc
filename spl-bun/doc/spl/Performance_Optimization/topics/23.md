3.8
多索引合并
前面的章节提到多个索引不能同时使用。为两个字段分别建立索引后，联合条件查询只能使用其中一个索引，另一个字段的条件仍需遍历判断。
实际上并非总是如此。对索引查询算法做一些优化，仍可在一定程度上让多个索引协同工作。
为便于叙述，记满足 x 的记录集合为 S(x)。假设表中字段 A 和 B 都有索引，要找 S(A==a && B==b)。
使用 A 的索引可快速定位 S(A==a)，但要在其中找到 S(B==b) 的记录，就不能再使用 B 的索引，反之亦然。
一般来说，索引中记录的物理位置也是有序的，即 A 的索引中，S(A==a) 的记录物理位置从小到大排列；B 的索引类似。这在建索引时容易满足，甚至是自然满足，因为排序时同值记录的原始顺序通常不会改变。
利用这一点，在检索 S(A==a && B==b) 时可以同时使用 A 和 B 的索引。做法不复杂：用 A 的索引得到基于 S(A==a) 的游标，用 B 的索引得到基于 S(B==b) 的游标。两个游标按物理位置有序，然后用归并算法求交集得到 S(A==a && B==b)。这等价于分别遍历一次 S(A==a) 和 S(B==b)，两个索引都参与了计算。
不过该算法在复杂度上不一定优于在 S(A==a) 中遍历并判断 B==b，因为后者只需遍历 S(A==a) 一次，而前者要遍历两个集合。
这种方法的优势在实践中：用归并求交集无需读取原始数据表来判断 B==b，只需比较索引。索引块可能已在内存中，即便在外部存储中也连续存放，只有两列（待检索键和物理位置）且为行式存储，读取性能远好于包含多字段、非连续存储和列式存储的原始数据集。因此归并与比较的性能会优于读记录再判断。
如果以 S(A==a) 与 S(B==b) 中较小的那个为基准与较大的做归并，只要较小者遍历完即可停止，较大集合中未遍历到的成员可直接忽略。这样遍历总量不会很大。建索引时通常可以知道 S(A==a) 的记录数。
当然，这种方法也适用于更多字段条件的情况。
SPL 已实现该机制。对于写在游标上的多字段条件，如 A==a && B==b && …，SPL 会自动寻找可用索引并合并，无需程序员干预。
