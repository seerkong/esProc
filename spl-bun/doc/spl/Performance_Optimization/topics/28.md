4.3
并行遍历
我们在第 2 章讨论过外部存储数据集的分段方法。该方法不仅可用于二分检索，更重要的是可用于分段并行计算。让多个 CPU 分摊计算量，往往可以实现接近线性增长的性能提升。
SPL 提供了简便的并行计算语法：
|
=file("orders.txt")
|
fork to(4)
|
=A1.cursor@t(area,amount;A2:4)
|
return B2.groups(area;sum(amount):amount)
|
=A2.conj().groups(area;sum(amount))
fork 语句会启动多个线程并行执行各自代码块。线程数由 fork 后参数序列长度决定，同时 fork 会依次把参数分配给线程。代码块中引用 fork 所在单元格的值即可获取该参数。所有线程执行结束后，各线程代码块的 return 结果会回收到 fork 所在单元格，并按线程顺序组成序列，然后继续执行后续代码。
此例中，A2 会生成 4 个线程，每个线程分别获取 1、2、3、4 作为参数，生成对应的分段游标 B2 进行分组聚合。四个线程完成后，return 的值（表序列）会聚合到 fork 单元格（A2），再将这些表序列拼接并再次聚合，得到原数据表的分组聚合结果。
除数据表分段外，还可用于多个文件的并行计算。例如订单按月分成 12 个文件，计算各地区金额超过 50 的订单数量：
|
fork to(12)
|
=file("orders"\A2\".txt")
|
=B1.cursor@t(area,amount;A2:4)
|
=B2.select(amount>=50)
|
return B2.groups(area;count(1):quantity)
|
=A1.conj().groups(area;sum(quantity))
这将启动 12 个线程。注意线程内使用 count() 时，线程外应使用 sum()，而不是 count()。
SPL 简化了并行计算机制，假设所有线程同时启动，任务在所有线程完成时结束。虽然无法处理系统级复杂并行任务，但语法与代码更简单，足以满足多数结构化数据计算。

设置后，SPL 会实际生成不超过该数值的线程。若 fork 参数序列更长，则会强制串行执行。例如上例中 fork 参数长度为 12，而并行数设为 4，则 SPL 实际只启动 4 个线程，把前四个任务依次分配给线程执行。线程执行完毕后变为空闲，再填入尚未执行的任务，循环直到全部完成。逻辑上看似 12 个线程，实际上只有 4 个。
在该机制下，任务拆分有益处。由于每个任务执行时间不一定相同，如果每个线程只执行一个任务，快线程完成后必须等待慢线程。拆分后，快线程可执行更多任务，总等待时间更少，负载更均衡，整体性能更好。但拆分也有缺点：占用更多内存存放线程结果，线程切换与调度也有成本，因此并非“拆得越多越好”，需根据实际情况确定合适的值。
通常每个线程由一个 CPU 执行。若线程数超过 CPU 数量，操作系统会用时间片切换不同线程，消耗 CPU 和内存资源，导致整体性能下降。因此并行数最大不应超过 CPU 数量，通常略少，因为 CPU 还要处理操作系统等任务。
有些服务器 CPU 很多，可能多达几十个，但设置更高并行数并不一定更快。一是线程调度成本上升，二是更常见的原因是硬盘没有同等的并行能力。多个线程共享同一组硬盘，外部存储计算时数据仍需从硬盘读取，而硬盘总吞吐能力有限，达到上限后无法更快，导致 CPU 空转等待硬盘。尤其是机械硬盘，并行读取会加剧磁头寻道，显著降低硬盘性能，很可能出现“并行读取越多，性能越差”的现象。
服务器的 CPU 与硬盘配置应当平衡以适配计算任务。有些服务器配备大量高端 CPU，却为了容量使用低速机械硬盘，往往无法发挥 CPU 效率造成浪费。若把 CPU 的预算部分用于内存或高速 SSD，可能花费更少而获得更好性能。
