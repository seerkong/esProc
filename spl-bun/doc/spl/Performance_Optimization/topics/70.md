## 提取内容
9.7
多作业负载均衡
类似单机多线程并行计算，上文介绍的多机并行计算框架也会等待最慢的节点返回结果后再继续。我们可以尽量让各节点的计算量更均衡，但无法保证节点执行速度一致，因此快节点等待慢节点的现象仍不可避免。在多数情况下影响不大，但在追求极致性能时不可接受。
理论上，就像处理多线程一样，可以把任务拆分成更小的作业并动态分配，以平衡各节点负载、减少等待。然而多机情况更复杂，因为动态负载均衡只能在数据冗余的前提下实现。如果某份数据只保存在一个节点上，那么只能由该节点计算；即便其他节点更快，也只能等待，否则就需要通过网络传输数据，不仅引入网络延迟，还会消耗数据所在节点的计算资源，得不偿失。单机多线程共享存储数据，因此不存在这个问题。
|
["192.168.0.101:8281","192.168.0.102:8281",…,
"192.168.0.104:8281"]
|
=callx("sub.dfx",to(1000);A1)
callx() 函数可以实现该机制。参数中的 sub.dfx 是节点上的作业计算脚本，以作业号为参数。A2 会生成 1000 个作业，起初只分配部分作业，使各节点作业数达到上限；随后完成作业的节点会被分配新作业，从而实现动态负载均衡。当因某作业数据不在分配节点而导致计算错误时，callx() 会把该作业重新分配到其他节点。若没有任何节点能执行该作业，计算失败。
计算结束时，A2 将获得由每个 sub.dfx 返回值组成的序列，顺序按作业号排列。
当作业量很大时还有一个问题：每个作业完成后都会将结果返回主机，导致返回次数过多，从而加重网络负担。幸运的是，很多操作允许节点先进行一轮聚合后再返回结果，这样返回次数可减少到节点数。
callx() 还有一个参数，用于指定先聚合的运算脚本。

["192.168.0.101:8281","192.168.0.102:8281",…,
"192.168.0.104:8281"]
|
=callx("sub.dfx",to(1000);A1;"reduce.dfx")
|
=A2.sum()
假设计算任务是求各 sub.dfx 返回值之和，则 reduce.dfx 代码为：
|
return p1+p2
其中 p1 和 p2 是 reduce.dfx 的两个参数，p2 是每个作业的返回值，p1 是节点当前的聚合值。每次节点完成一个作业都会调用 reduce.dfx，以获取新的聚合值替换当前聚合值。节点完成所有作业后，会把最后的聚合值作为其返回值传回主机。此时 A2 得到由所有节点返回值组成的序列，顺序与其参数（即 A1）中的节点顺序一致。这里的 p1 和 p2 有点类似迭代函数中的 ~~ 和 ~。
在分布式计算术语中，节点执行的这种聚合动作称为 reduce。
